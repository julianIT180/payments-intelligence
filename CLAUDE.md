# Payments Intelligence — project instructions

Automated research pipeline for the payments/fintech industry. Three n8n workflows
retrieve sources, filter them in stages, have Claude models judge and analyse them,
and write evidence-scored briefs into Postgres. A Next.js site reads that database.

Core differentiator: a source-grounded, evidence-scored payments intelligence
pipeline. Retrieval quality, filtering, provenance, confidence handling and the
ability to return "insufficient evidence" matter more than simply using a powerful
LLM. Rules check format; models assess content.

## Repository layout

- `workflows/`  n8n workflows as exported JSON. Machine-generated. Do not hand-edit.
- `db/`         `schema.sql` (tables, RLS, grants), `metrics.sql` (reporting queries).
- `web/`        Next.js frontend (App Router, Tailwind), deployed on Vercel, root dir `web`.
- `docs/`       `architecture.md` (Mermaid diagrams), `progress.txt` (German dev log).

## Secrets and data — non-negotiable

- Never put API keys, tokens, passwords, connection strings or credentials in code,
  docs, commit messages or history. Example env files may hold placeholders only.
- Never read, print or commit `web/.env.local`.
- Analytics features use synthetic data only. Never commit employer, client or
  confidential material.
- Before any commit: check `git status`; confirm no `.env`, no keys, no `node_modules`.

## Workflows

- `workflows/*.json` are exports. Edits made here are lost on the next export from
  n8n; make workflow changes in n8n and re-export.
- Do not change Anthropic model IDs, run frequency, volume or model tier without an
  explicit decision. Model choice follows task difficulty (Haiku for triage and
  extraction, Sonnet for analysis and synthesis).
- Two refusal layers must both stay intact: the model-level `INSUFFICIENT EVIDENCE`
  return in `Analyse and Draft Brief`, and the four-condition publication gate in
  `Prepare DB Record` / `Persist Brief?` (`model_refused` false, `had_enough_evidence`,
  `source_count >= 3`, `confidence_score >= 40`). Do not relax a source-quality or
  publication threshold without an explicit decision.
- Known live risks — do not silently "fix": Tavily pay-as-you-go is on; the n8n form
  trigger has no authentication (safe only while n8n is local).

## Frontend conventions

- Prefer Server Components and server-side data fetching by default.
- Use Client Components, Server Actions, API routes or client state only when a
  feature genuinely requires interactivity, uploads, mutations or browser-side
  behaviour. Keep client-side complexity minimal and justify significant deviations
  from the existing architecture.
- Application code is `.js`, not `.tsx`, by choice. The TypeScript toolchain stays installed.
- The existing read-only pages each set `export const revalidate = 300;` and query
  Supabase directly via `lib/supabase` with the publishable (anon) key. On a query
  error they render the red box from `app/page.js`
  (`border-red-300 bg-red-50`, `text-red-800`) rather than throwing.
- Design language from `app/page.js`: `bg-stone-50` page, `bg-white` cards,
  `border-stone-200`, container `mx-auto max-w-4xl px-6`, dates `en-GB`
  (`day: '2-digit', month: 'short', year: 'numeric'`). UI text English; existing
  code comments are German — keep that.
- `web/AGENTS.md` and `web/CLAUDE.md` are auto-generated by `next dev` and gitignored.
  Do not commit them; do not rely on them for project rules.

## Database

- `db/schema.sql` is the source of truth for table shape. Do not rewrite it; add
  changes as new migration files.
- Read access needs both a `grant select … to anon` and an RLS policy —
  "Automatically expose new tables" is off in this Supabase project.
- Aggregations for the frontend belong in Postgres views (`db/views.sql`, planned),
  created with `security_invoker = true` plus an explicit `grant select … to anon`.
